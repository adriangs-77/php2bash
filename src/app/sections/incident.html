Anatomía del fallo

03¿En qué consiste la vulnerabilidad?

No hay inyección SQL ni XSS: el problema está en cómo PHP gestiona la memoria cuando una petición muere a mitad. Dos CVE, un mismo patrón: publicar estado, hacer después algo que puede fallar y no deshacer lo publicado si el fallo es fatal. La siguiente petición del mismo worker hereda basura y la trata como datos válidos.

El modelo mental: el worker que no olvida

PHP-FPM y mod_php reutilizan procesos para atender muchas peticiones. Cada petición tiene su propio heap, que se libera al terminar. Si un error fatal interrumpe el intérprete mediante longjmp(), el código de limpieza no se ejecuta: ni destructores, ni rollback, ni reinicio de contadores. Algunas variables globales siguen apuntando a memoria ya liberada.

Petición A · el atacante fuerza un fatal
Una petición multipart/form-data hace que PHP agote memory_limit mientras inicializa estructuras internas o decodifica la sesión. El heap de la petición se destruye.
El worker sobrevive con punteros colgantes
El estado global (backtrace del último fatal, contexto del unserializer, PS(id) de la sesión, OPcache) no se reinicia. Apunta a direcciones que ya no le pertenecen.
Petición B · el atacante reclama esa memoria
Con asignaciones controladas rellena el hueco con sus propios datos. El worker los interpreta como bookkeeping legítimo: obtiene lectura de memoria y primitivas de corrupción.
Resultado: ejecución de código o fuga de memoria
Encadenando fugas y escrituras se consigue zend_call_function() → una orden del sistema con los privilegios del usuario web. O simplemente se exfiltra memoria de otras peticiones.

Corrupción por OOM (out-of-memory)

El agotamiento de memoria interrumpe a PHP mientras los datos internos de la petición están solo parcialmente inicializados. La rutina de limpieza posterior procesa ese estado inválido.

  • Vector demostrado: use-after-free del unserializer de session.upload_progress.
  • Consecuencia: RCE y, por separado, divulgación de memoria del proceso sin autenticación.
  • Demostrado en: mod_php con scripts PHP arbitrarios (≥ 7.3) y RCE pre-autenticación en WordPress, Drupal y Joomla.

Estado global obsoleto (stale state)

El estado interno propiedad de una petición sobrevive a la liberación de su memoria. Una petición posterior, atendida por el mismo worker, lo usa antes de que la inicialización normal lo restablezca.

  • Vectores: backtrace del último error fatal (EG(last_fatal_error_backtrace)) y confusión de tipos en OPcache compartido.
  • Consecuencia: RCE; también use-after-free entre peticiones y corrupción de estado compartido entre workers.
  • Demostrado en: RCE pre-autenticación en Drupal (backtrace) y WordPress (OPcache), además de la ruta de sesión validada contra PHP-FPM.

¿Por qué se llama PHP2Shell (y php2bash)?
El nombre nace del exploit combinado que Wiz y Calif construyeron: PHP to shell. El objetivo final de la cadena es convertir una petición HTTP en una shell en el servidor. En este repositorio el proyecto se llama php2bash por el mismo motivo: PHP → bash. Las CVE son la causa; «php2shell» es la herramienta/exploit.
El patrón, en código

Publicar antes de terminar de construir

El bug original está en el orden de operaciones de la tabla hash de PHP. El contador de elementos se incrementa antes de que el bucket esté inicializado. Si la asignación de la clave falla por falta de memoria, el fatal salta y el bucket queda a medias; pero el contador ya lo hace visible al destructor de la tabla.

Reproducido de forma divulgativa a partir del análisis de Calif. No es código explotable: los detalles de asignación, bytes y offsets se omiten a propósito.

Cómo se fuerza el fatal

Todo ocurre durante el arranque de la petición, antes de que se ejecute una sola línea de tu aplicación. Por eso no hay nada que arreglar en el código de Laravel: el problema ya ha sucedido cuando public/index.php empieza a correr.

  • post_max_size se compara con el Content-Length declarado, no con los bytes reales consumidos.
  • Una parte con filename="" no cuenta para max_file_uploads, pero crea seis claves en $_FILES.
  • Nombres anidados (files[a][b][c]…) multiplican las asignaciones: cientos de registros ocupan más de 128 MiB sin superar 8 MiB de cuerpo.

Por qué el SAPI importa tanto

El mismo fallo tiene distinto alcance según cómo se ejecute PHP. La diferencia clave es si el proceso sobrevive al fatal.

De ahí la prioridad que da PHP: mod_php es el escenario más grave, porque permite el ataque con una sola petición y antes de que la aplicación exista. En PHP-FPM la ruta de sesión se validó igualmente, y la de OOM es vulnerable por análisis.

1Ejecutar código

RCE como el usuario web (www-data, nginx, apache). Desde ahí: leer .env, la base de datos, claves de AWS o Stripe, escribir un webshell, moverte lateralmente.

2Leer memoria

La variante de fuga devuelve memoria del worker dentro de una cookie PHPSESSID. Puede contener contraseñas, tokens de sesión, claves de API y certificados TLS de otras peticiones. Funciona incluso si la aplicación nunca llama a session_start().

3Denegar servicio

El propio disparador agota memoria y provoca caídas o reciclado de workers (SIGSEGV). Sin llegar a RCE, ya es un impacto real sobre disponibilidad y coste.

Matiz importante: no es un «gusanos tipo Log4Shell»
El vector CVSS es AV:N/AC:H/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H: complejidad alta. El ataque necesita conocer la configuración del objetivo y, a menudo, repetir intentos para acertar con la disposición de memoria del worker. Varios PoC públicos no funcionan contra una instalación PHP por defecto y algunos solo lo hacen tras añadir un local file inclusion al servidor de pruebas. Eso reduce la probabilidad de explotación masiva indiscriminada, pero no reduce la gravedad para un objetivo concreto y bien estudiado.
